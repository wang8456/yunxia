# 原版听译方案（subs-hub + asr-worker）

开源版把听译收进服务端一个进程里；**原版是两台机器分工**，因为当年跑转写的电脑和存片的 NAS 不是同一台，
而 NAS 上装不动 whisper（aarch64、内存小）。

这份文档记录原来那套是怎么转的，以及踩过哪些坑——想自己实现「分布式听译」的话可以直接抄结构。

## 一、拓扑

```
手机/浏览器 (网页端 SubsView.vue / App subs_*）
        │  ① POST /job {url,name,model}
        │  ④ GET  /job/<id>  轮询拿增量段落
        ▼
┌──────────────────────────────┐
│  NAS  subs-hub.py  :5092      │  轻活：任务表、字幕缓存、翻译
│  · jobs/<id>.json             │  一直开着，内存几百 MB
│  · audio/ 抽好的 16k flac      │
│  · 翻译线程 → DeepSeek API     │
└──────────────────────────────┘
        ▲  ② GET  /work?wait=25   长轮询领活（电脑出站，不用改防火墙）
        │  ③ POST /cue {segs}      每转完一块立刻推回来
        │  POST /finish | /fail
┌──────────────────────────────┐
│  电脑  asr-worker.py          │  重活：ffmpeg 抽音 + whisper 转写
│  · 可多槽并发（MAX_SLOTS）      │  内存几个 G，跑完就闲着
└──────────────────────────────┘
```

设计取舍：**电脑主动来拉活**（出站长轮询），NAS 不需要知道电脑的地址，电脑换 IP、开关机、走 Tailscale 都不影响。
代价是延迟：最长 `wait=25` 秒才发现有新任务（所以新任务进来时会打断长轮询，见 `pick_work`）。

## 二、任务流

```
POST /job  →  state=queued，落 jobs/<id>.json
              ├─ 同一部片重复提交：按 url 去重，直接返回 done 的那份（reused=true）
              └─ max_active 到了（默认 3，算 queued+asr+translating）就排队

worker 领活 →  state=asr，claim 一下防止两个 worker 抢同一条
worker 推段 →  POST /cue {segs:[[起,止,原文]], done_until, lang}
              中枢把这些段并进 job，交给翻译线程补齐第 4 列
worker 收尾 →  POST /finish {lang,dur} → asr_done=true
翻译补齐    →  所有段都有译文 → state=done
出错        →  POST /fail {msg} → state=error（msg 直接显示给用户）
```

状态：`queued → asr → translating → done`，另有 `error` / `cancelled`。
排序用 `RANK = {done:0, translating:1, asr:2, queued:3}`，列表里在跑的排前面。

## 三、接口（够写一个兼容客户端）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/job` | `{url,name,model}` → `{id,state,reused}`，客户端从这里起任务 |
| GET | `/job/<id>` | `{state,lang,done_until,msg,segments:[[起,止,原文,中文]]}`，**每次给全量**，前端自己合并 |
| GET | `/work?wait=25` | 只给 worker 用：领一条活，没有就挂 25 秒后返回 204 |
| POST | `/cue` | worker 推增量段（带 `done_until`，中枢据此判断「转写到第几秒」） |
| POST | `/finish` | worker 说「这条转完了」，之后只等翻译 |
| POST | `/fail` | 带错误原因，直接进 `error` |
| POST | `/cancel` `/delete` | 用户停止 / 删除任务（连段落一起删） |
| GET | `/jobs` | 队列总览（听译监控页用） |
| POST | `/config` | `{max_active}` 改同时处理上限 |
| GET | `/health` | `{ok, key:bool, jobs:N}`，顺手能看出 Key 配没配 |
| POST | `/reset` | 把卡住的 `asr` 打回 `queued` |
| POST | `/live` | 实时听译（边看边转，见第六节） |
| POST | `/atrack` | 客户端选音轨，worker 跟着这个流序号抽音 |

## 四、转写为什么要分块

一次性 `ffmpeg -i` 抽完整片音频再交给 whisper，在 4K 大文件上要 9–10 分钟，
这段时间用户只看到「已听译 0 秒」，以为坏了。

所以 worker 是**边抽边转**：

- `CHUNK_FIRST = 45` 秒：第一块故意短，让**首条字幕 30 秒内出现**
- `CHUNK = 60` 秒：之后每块一分钟（原来 180，实时听译要插队时最多等 3 分钟，所以缩短）
- 抽音在后台线程里不停把 PCM 写进环形缓冲，转写只从缓冲里取 —— 两个动作并行，不串行等待
- 每块转完立刻 `/cue` 推回去，网页端显示进度就是按 `done_until / 片长` 算

**按语言挑音轨**：MULTi 资源默认音轨经常是英语配音，不挑就等于在给配音轨做听写。
`ffprobe` 拿到所有音轨的语言标签，按 `LANG_PREF = [zho, chi, cmn, yue, kor, jpn, eng]` 排序，优先中日韩。

引擎二选一：`--engine fw`（faster-whisper，默认）或 `--engine cpp`（whisper.cpp）。
模型：`turbo` = large-v3-turbo，`small` = small；fw 走 HF 模型 id，cpp 走 `ggml-*.bin`。

## 五、翻译线程（在 NAS 上跑，不占电脑）

- 每批 `BATCH = 12` 段送给 DeepSeek，要求「只输出译文，一行对一行」
- `INFLIGHT` 集合标记在翻的下标，两条线程不会翻同一批
- 翻完一批再挑下一批；所有段都有第 4 列 → `done`
- **连续失败 3 次或转写已经结束**：拿原文顶上，前端至少还能看原文

  > 这是原版和开源版最大的一处行为分歧。开源版宁可留空也不拿原文冒充译文，
  > 因为「有中文」和「中文就是原文」在界面上一模一样，用户会以为翻译坏了。

## 六、实时听译（live）

`POST /live` 建的任务带 `live=1` 和 `live_from`（当前播放位置）：
worker 不再从 0 开始，而是**跟着播放头**转，一窗 `LIVE_WIN = 12` 秒、相邻窗重叠 `LIVE_OV = 2` 秒防断句。

追上「播放头 + 预读」之后**不退出**，而是挂起等播放头前进，ffmpeg 和缓冲保持打开——
早期版本每次续窗都重开 ffmpeg，缓冲从 0 爬到 45 秒，白白扔掉 3–10 秒，
用户体感就是「字幕到播放位置就不长了」。

`live` 任务在队列里有优先权（`live_busy` 判断 + 插队）。

## 七、保活与幽灵任务

- 两个看门狗：`nas-subs-hub.initd`（NAS 开机自起）+ `nas-subs-hub-watchdog.sh`、`asr-watchdog.sh`（PC 定时拉活）
- 中枢 `state=asr` 但 `touch` 超过 600 秒没更新 → 认为 worker 死了，打回 `queued`
  （否则界面会一直显示「转写中」，永远不动，也就是所谓的**幽灵任务**）
- 反过来，`asr` 且最近有心跳 → 保留，不能把正在干的活抢走

## 八、踩过的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| PyAV 解码 | `av>=16` 上 `metadata_errors` 参数没了，faster-whisper 直接抛 TypeError | 不喂文件给 faster-whisper，改成**自己读 ffmpeg 出的 wav** 再转（开源版则锁 `av>=12,<16`） |
| 整片抽音太慢 | 4K 片 9–10 分钟没字幕 | 分块 + 首块 45 秒 |
| 默认音轨是配音 | 转出来是英文配音的听写 | ffprobe 按语言挑轨 + 客户端 `/atrack` 覆盖 |
| 续窗重开 ffmpeg | 实时字幕卡在某一秒不长 | 追上后挂起等播放头，不退出 |
| 幽灵任务 | 「转写中」永远不动 | 心跳超时 600 秒打回队列 |
| 翻译挂了整片没字幕 | 用户以为听译坏了 | 三次失败后用原文顶替（开源版改成留空并提示） |
| 两处协作难部署 | 换台机器就全套不work | 开源版直接内置 whisper 子进程 |

## 九、客户端那一侧（原版网页/App 都做了）

- 播放器字幕面板：开关（关/原文/双语）、字号、位置微调、延时校准、单双语切换
- `/subs/at` 心跳：播放器定期报告「我还在看这条、播到第几秒」，中枢据此保持实时任务活性
- 文件页行菜单：生成字幕 / 查看作业
- 听译监控页：队列、进度、取消、重新转写、导出 SRT
- `srt.ts`：把段落拼成 SRT（双语时两行一条）
- PGS 图形字幕（内封蓝光字幕）单独走播放器渲染，和听译文本字幕是两套

这些前端在 `web/src/views/`（`SubsView.vue`、`SubsSettingsView.vue`、`Preview.vue`）和
`app/lib/ui/`（`subs_page.dart`、`subs_view_page.dart`、`subs_monitor.dart`、`player_subs.dart`）里，
开源版重写了同名功能的精简版本，可以直接对照。
